Werkzeugkasten

Heute neu in Python: assert mit AssertionError, Testfunktionen mit def test_...():, Testfälle als Liste von Tupeln mit Schleife und except AssertionError as fehler. Dazu Vorgehensweisen: Testwerte aus Bereichen und Grenzen ableiten und Fehler mit print und „Schritt für Schritt“ finden. Aus V07 setzen wir def und return voraus, aus V08 Listen, Tupel und for, aus V09 try/except, aus V03 math.isclose und f-Strings. Die Klausur verlangt, dass du Code von Hand schreibst. Darum gehen wir in kleinen Schritten vom Vormachen zum Selberschreiben, und die Hilfen werden dabei weniger.

Merke

Diese acht Syntax-Karten sind dein Spickzettel, bis es sitzt. Du erreichst sie in jeder Aufgabe über den Knopf „Werkzeugkasten“ oben. Alle Befehle des Kurses stehen außerdem rechts in der Befehls-Bibliothek. Führe jede Karte aus und drück bei den Schleifen auf „Schritt für Schritt“.

Syntax-Karte 1

assert: eine Behauptung prüfen

def kmh_in_ms(v):
    return v / 3.6

assert kmh_in_ms(36) == 10.0
assert kmh_in_ms(72) == 20.0, "72 km/h müssen 20 m/s sein"
print("Beide Tests bestanden")
  • assert bedingung prüft eine Behauptung. Ist die Bedingung wahr, passiert nichts. Ist sie falsch, bricht Python ab und löst einen AssertionError aus.
  • Hinter dem Komma steht eine Meldung (ein Text), die nur im Fehlerfall erscheint: assert bedingung, "Meldung". Gute Meldungen nennen den Eingabewert, den erwarteten und den bekommenen Wert.
  • Das Erwartete rechnest du von Hand aus der Spezifikation aus (hier: 36 km/h sind 10 m/s). Nimm nie das Ergebnis der Funktion selbst als Erwartung.
  • Schreibe das assert ohne Klammern um Bedingung und Meldung. Mit Klammern entsteht ein Tupel, und ein nicht leeres Tupel ist immer wahr: Der Test prüft dann nichts.
Syntax-Karte 2

Testfunktion: def test_...() und selbst aufrufen

def kmh_in_ms(v):
    return v / 3.6

def test_kmh_in_ms():
    assert kmh_in_ms(0) == 0.0
    assert kmh_in_ms(36) == 10.0
    assert kmh_in_ms(-36) == -10.0, "negative Geschwindigkeit"
    print("test_kmh_in_ms: bestanden")

test_kmh_in_ms()
  • Mehrere assert-Zeilen gehören in eine Testfunktion. Der Name beginnt mit test_ und nennt, was getestet wird. Übliche Schreibweise: ein Test pro Funktion.
  • Die Funktion läuft erst, wenn du sie selbst aufrufst (letzte Zeile). Am Ende steht eine print-Zeile mit „bestanden“, denn bei Erfolg schweigt assert.
  • Der Test ruft die getestete Funktion nur auf. Sie darf weiter oben oder weiter unten im Programm definiert sein, solange sie vor dem Aufruf des Tests existiert.
  • Der erste scheiternde assert beendet die Testfunktion. Alle weiteren Zeilen laufen dann nicht mehr.
Syntax-Karte 3

Testfälle als Liste von Tupeln mit Schleife

def drehzahl_ampel(n):
    if n < 0:
        return "ungueltig"
    elif n < 3000:
        return "gruen"
    elif n <= 4500:
        return "gelb"
    else:
        return "rot"

faelle = [
    (-1, "ungueltig"),
    (0, "gruen"),
    (2999, "gruen"),
    (3000, "gelb"),
    (4500, "gelb"),
    (4501, "rot"),
]
for n, erwartet in faelle:
    tatsaechlich = drehzahl_ampel(n)
    assert tatsaechlich == erwartet, f"n = {n}: erwartet {erwartet}, bekommen {tatsaechlich}"
print(len(faelle), "Testfälle bestanden")
  • Jeder Testfall ist ein Tupel (V08) aus Eingabe und erwartetem Ergebnis, alle zusammen stehen in einer Liste. Neue Fälle sind nur eine neue Zeile.
  • for n, erwartet in faelle: packt jedes Tupel in zwei Namen aus, wie for teil, werte in ...items() in V08. Das assert im Rumpf prüft jeden Fall.
  • Die Meldung ist ein f-String (V03) mit den Werten: Scheitert ein Fall, siehst du sofort, welcher. Ohne diese Meldung steht im Traceback nur AssertionError.
  • Die Reihenfolge im Test: erst tatsaechlich berechnen, dann vergleichen. So ist die Zeile lesbar.
Syntax-Karte 4

Testwerte ableiten: Bereiche und Grenzen

# Spezifikation: n < 0 ungueltig | 0 <= n < 3000 gruen | 3000 <= n <= 4500 gelb | n > 4500 rot
bereiche = [-500, 1500, 4000, 6000]          # je Bereich ein typischer Wert
grenzen = [-1, 0, 2999, 3000, 4500, 4501]    # jede Grenze von beiden Seiten
sonder = [0]                                 # Sonderfälle (hier schon in den Grenzen)
print(len(bereiche) + len(grenzen), "Testwerte, davon", len(grenzen), "an Grenzen")
  • Bereiche: Zerlege die Spezifikation in Bereiche, in denen sich die Funktion gleich verhält. Je Bereich ein typischer Wert genügt.
  • Grenzen: An jeder Grenze testest du den letzten Wert, der noch drin ist, und den ersten, der schon draußen ist. Bei ganzen Zahlen sind das Nachbarn (2999 und 3000), bei Kommazahlen wählst du einen kleinen Abstand (69,9 und 70).
  • Sonderfälle: 0, negative Werte, eine leere Liste, der kleinste und der größte erlaubte Wert.
  • Frage bei jedem Wert: Was erwarte ich laut Spezifikation? Rechne es auf Papier aus, bevor du den Code der Funktion ansiehst.
Syntax-Karte 5

Kommazahlen vergleichen: math.isclose

import math

def umfang(d):
    return 3.14159265 * d

assert math.isclose(umfang(2.0), 6.2831853, rel_tol=1e-6), "Umfang falsch"
assert abs(umfang(1.0) - 3.14159265) < 1e-9, "Umfang falsch"
print("0.1 + 0.2 == 0.3 ist", 0.1 + 0.2 == 0.3)
print("math.isclose(0.1 + 0.2, 0.3) ist", math.isclose(0.1 + 0.2, 0.3))
  • Berechnete Kommazahlen sind selten exakt gleich (V03): 0.1 + 0.2 == 0.3 ist falsch. Beim Test vergleichst du sie darum mit Toleranz.
  • math.isclose(a, b, rel_tol=1e-6) prüft, ob a und b sich relativ um höchstens ein Millionstel unterscheiden. Alternativ abs(a - b) < 1e-9.
  • Texte, ganze Zahlen und Wahrheitswerte vergleichst du weiter mit ==. Ebenso Kommazahlen, die nur festgelegte Werte zurückgeben (return 4.90).
  • Die Toleranz gehört in die Spezifikation: Was ist „gleich genug“ für dein Bauteil?
Syntax-Karte 6

AssertionError abfangen: except ... as fehler

def zustand_ki(t):
    if t < 70:
        return "normal"
    elif t < 85:
        return "warnung"
    else:
        return "abschalten"

faelle = [(69.9, "normal"), (70, "warnung"), (85, "warnung"), (85.1, "abschalten")]
gescheitert = 0
for t, erwartet in faelle:
    try:
        assert zustand_ki(t) == erwartet, f"{t} °C: erwartet {erwartet}, bekommen {zustand_ki(t)}"
    except AssertionError as fehler:
        gescheitert = gescheitert + 1
        print("GESCHEITERT:", fehler)
print(gescheitert, "von", len(faelle), "Tests gescheitert")
  • Ohne try beendet der erste Fehler das Programm. Mit try/except AssertionError (V09) läuft die Schleife weiter, und du siehst alle gescheiterten Fälle.
  • as fehler ist neu: Es gibt der Ausnahme den Namen fehler. print(fehler) druckt dann deine Meldung aus dem assert. Der Name ist frei wählbar, fehler oder e sind üblich.
  • Fang nur AssertionError. Ein NameError im Test (Tippfehler) soll weiter auffallen.
  • Der Zähler gescheitert gibt dir am Ende eine Bilanz.
Syntax-Karte 7

Fehler lesen: Traceback von unten nach oben

def mittelwert(werte):
    return sum(werte) / len(werte)

def auswerten(reihen):
    for r in reihen:
        print(mittelwert(r))

auswerten([[20, 22], []])
  • Letzte Zeile: Fehlerart und Meldung (ZeroDivisionError: division by zero): was ist passiert. Davor: die Fehlerstelle mit Datei, Zeile und Funktion (in mittelwert): wo. Darüber: die Aufrufer (in auswerten, in <module>): wie kam es dazu.
  • Fehlerarten: Syntaxfehler (SyntaxError, IndentationError) meldet Python vor dem Start. Laufzeitfehler (NameError, TypeError, ValueError, ZeroDivisionError, IndexError) tritt beim Ausführen auf. Ein Logikfehler hat gar keine Meldung: Das Ergebnis ist einfach falsch.
  • Die Ursache liegt oft weiter oben als die Fehlerstelle: Hier in der leeren Liste, die auswerten übergibt.
  • Ein AssertionError zeigt die Stelle des Tests, nicht des Fehlers im Programm: Dort musst du selbst suchen.
Syntax-Karte 8

Fehler finden: Hypothese, print, Schritt für Schritt

def hoechstwert(werte):
    groesster = 0
    for w in werte:
        print("w =", w, "| groesster =", groesster)     # Beobachtung
        if w > groesster:
            groesster = w
    return groesster

print("Ergebnis:", hoechstwert([-5, -2, -8]))
  • Der Zyklus: (1) Test scheitert. (2) Hypothese: Was ist die wahrscheinliche Ursache? (3) Beobachten: sichtbar machen, was wirklich passiert. (4) Korrigieren: eine Sache ändern. (5) Test erneut: alle Tests.
  • print an der verdächtigen Stelle: Gib nicht nur den Wert aus, sondern auch das, was entscheidet (hier groesster und der Vergleich). Entferne die Zeilen danach wieder.
  • Schritt für Schritt (Knopf unter jedem Codefeld): Der Visualisierer zeigt Zeile für Zeile, welche Variable sich ändert. Hier siehst du, dass groesster bei 0 stehen bleibt: Bei negativen Werten ist 0 größer als alles. Hypothese bestätigt.
  • VS-Code-Debugger (nur Ansicht, in Codespaces): roter Haltepunkt am Zeilenrand, dann starten. Fenster Variablen und Aufrufliste, Schritt über und hinein. Schema in der Lerneinheit und im Theorie-Video.

Vorgerechnetes Beispiel: Lagertemperatur mit neun Testfällen

Aufgabe: Die Funktion zustand bewertet die Lagertemperatur nach der Spezifikation aus der Lerneinheit. Gesucht sind Testfälle von Hand: je Bereich ein typischer Wert und jede Grenze von beiden Seiten, neun assert-Zeilen. Danach kommt die Version der KI, die an der Grenze 85 °C einen Fehler hat, und der Test findet ihn sofort. Lies den Code Zeile für Zeile, dann führe ihn aus. Die zweite Ausgabe ist die Meldung des gescheiterten Tests. Drück danach auf „Schritt für Schritt“ und beobachte, wie der assert bei der KI-Version in den except-Block springt.

Erwartete Ausgabe:

Alle 9 Tests bestanden
AssertionError: Grenzwert 85 °C falsch eingeordnet

Der Programmablaufplan der Funktion zustand zeigt die drei Rauten hintereinander und die vier Wege. Gib einen Wert ein oder klicke einen aus der Tabelle an: Jeder Pfad und jede Grenze ist ein Testfall. Die neun Tests im Code sind eine Auswahl daraus.

  1. Zeilen 1 bis 4: Kommentare mit der Spezifikation. Sie steht vor dem Code und den Tests: Daraus leitest du die Testfälle ab, nicht aus der Funktion.
  2. Zeilen 7 bis 16: Die Funktion zustand (V07). Die erste Frage in Zeile 9 sortiert die Sensorfehler aus (unter −40 oder über 200). Danach drei Zweige nach dem PAP: unter 70 normal, bis einschließlich 85 warnung (Zeile 13: <=), sonst abschalten.
  3. Zeilen 19 bis 24: Die Testfälle für die Bereiche normal, Warnung und abschalten. 20 ist der typische Wert für normal. Die Werte 69,9 und 70 sind die beiden Seiten der ersten Grenze, 85 und 85,1 die beiden Seiten der zweiten. Genau 70 gehört schon zur Warnung, genau 85 noch zur Warnung: Das ist der Kern der Spezifikation.
  4. Zeilen 25 bis 28: Die Grenzen der Sensorfehler. −40 ist noch eine gültige Messung (normal), −40,1 ist schon ein Sensorfehler. 200 ist noch gültig (abschalten), 200,1 ist ein Sensorfehler. Die Erwartung stammt auch hier aus der Spezifikation, nicht aus dem Programm.

Ablauf verfolgen

Bevor du Tests schreibst, musst du sie lesen können. Führe das Programm im Kopf aus, Zeile für Zeile, so wie Python es tut. Trage ein, was danach in den hervorgehobenen Variablen steht. Zahlen schreibst du ohne Anführungszeichen, Listen und Tupel so, wie Python sie ausgibt. Eine try-Zeile bekommt keinen eigenen Schritt. Bei einem assert gilt: Ist die Bedingung wahr, geht es einfach weiter, sonst springt Python sofort in den except-Block. Wenn unsicher: Lass den Code vorher im „Vorgerechneten Beispiel“ oder in Karte 6 mit „Schritt für Schritt“ laufen.

Zweiter Ablauf: Testfälle als Liste von Tupeln. Die Funktion plus_zwei soll laut Spezifikation 2 addieren, die KI hat aber mal 2 geschrieben. Beachte, wie ein Testwert den Fehler verdecken kann: Bei welchem Wert fällt er auf? Die Schleife entpackt jedes Tupel in zwei Namen, und die Zeile mit for ist ein Schritt je Durchlauf. Die Zeile mit dem Aufruf bringt den Parameter x.

Zeilen ordnen

Alle Zeilen sind da, aber durcheinander. Bring sie in die richtige Reihenfolge und rücke die Zeilen ein (Pfeil nach rechts oder Mausziehen). Manche Zeilen sind Ablenker: Sie gehören nicht ins Programm.

Testfunktion mit Testfällen

Die Testfunktion prüft die Porto-Funktion mit einer Liste von Tupeln (Gramm, Porto) und meldet am Ende „bestanden“. Die Meldung im assert nennt Eingabe, erwartet und bekommen. Die Funktion wird zum Schluss aufgerufen. Überlege vorher: Was steht eingerückt in der Schleife, und was gehört danach?

Gescheiterten Test abfangen

Das Programm prüft die Grenze 85 und meldet, wenn der Test scheitert. Bei Erfolg steht eine Meldung im try-Block, bei Misserfolg im except-Block. Das Wort as gibt der Ausnahme den Namen fehler.

Lücken füllen

Jetzt tippst du Teile selbst. Ergänze die fünf Lücken, sodass die Testfunktion alle Fälle der Drehzahl-Ampel prüft, einen gescheiterten Test mit Namen meldet und am Ende „bestanden“ ausgibt. Geprüft wird nicht nur dein Wortlaut, sondern ob das Programm das Richtige tut.

def drehzahl_ampel(n):
    if n < 0:
        return "ungueltig"
    elif n < 3000:
        return "gruen"
    elif n <= 4500:
        return "gelb"
    else:
        return "rot"

def test_ampel():
    faelle = [(-1, "ungueltig"), (0, "gruen"), (3000, "gelb"), (4501, "rot")]
    for n, erwartet in @@faelle@@:
        tatsaechlich = drehzahl_ampel(n)
        @@assert@@ tatsaechlich @@==@@ erwartet, f"n = {n}: erwartet {erwartet}, bekommen {tatsaechlich}"
    print("bestanden")

try:
    test_ampel()
except AssertionError @@as@@ fehler:
    print("GESCHEITERT:", fehler)
@@print@@("Test beendet")
  1. Lücke 1: Die Schleife geht über die Liste der Testfälle, die eine Zeile darüber steht und faelle heißt.
  2. Lücke 2 und 3: Das Wort für „behaupte“ (Karte 1) steht am Anfang der Zeile, dann folgt der Vergleich, mit zwei Gleichheitszeichen.
  3. Lücke 4: Hinter AssertionError gibt das kleine Wort der Ausnahme einen Namen (Karte 6). Lücke 5: Die letzte Zeile gibt den Text aus.

Erste eigene Aufgabe: Testfälle für die Drehzahl-Ampel

Jetzt schreibst du Testfälle selbst, und zwar die Art, die Fehler findet. Die Prüfung läuft in drei Schritten: Deine Testfälle müssen bei der richtigen Funktion bestehen (sonst hast du dich bei einem erwarteten Wert verrechnet). Dann läuft dieselbe Liste gegen mehrere fehlerhafte Varianten der Funktion, jede mit genau einem eingebauten Fehler (zum Beispiel < statt <=). Ein guter Test scheitert bei jeder fehlerhaften Variante. Besteht eine fehlerhafte Variante alle deine Tests, fehlt dir ein Testfall: Die Meldung sagt dir, welcher Fehler durchgerutscht ist.

Die Funktion drehzahl_ampel(n) ordnet eine Drehzahl in 1/min ein: unter 0 ungueltig (ein Sensorfehler), von 0 bis unter 3000 gruen, von 3000 bis einschließlich 4500 gelb, darüber rot. Ergänze die Liste faelle mit Tupeln (Drehzahl, erwartetes Ergebnis): je Bereich ein typischer Wert und jede Grenze von beiden Seiten, dazu den Sonderfall 0. Leite die erwarteten Werte aus der Beschreibung her, nicht aus dem Code. Die Schleife darunter prüft alle Fälle.

Szenario: Tests für die Lagertemperatur

Prompt eines Studierenden

Schreibe Tests für die Funktion zustand(t): unter 70 °C „normal“, von 70 bis einschließlich 85 °C „warnung“, über 85 °C „abschalten“, Messwerte unter −40 °C oder über 200 °C sind ein „sensorfehler“. Teste gründlich.

KI-Antwort (Python)

Tipp: Es sind drei Fehler eingebaut. Nicht jede Zeile ist falsch.

Würdest du das freigeben? Markiere die fehlerhaften Zeilen, dann lass auflösen.

Die drei Fehler

Fehler 1: nur Normalfälle (Zeilen 2 bis 4)

Die drei Werte 20, 75 und 90 liegen in der Mitte der Bereiche. Genau dort sind Fehler selten, sie sitzen an den Grenzen (70, 85) und bei den Sensorfehlern. Die KI schreibt gern den Fall, den ihr Code sowieso besteht. Ein Fehler wie < statt <= bei 85 würde alle drei Tests bestehen. Lösung: Grenzen von beiden Seiten (69,9 und 70, 85 und 85,1, −40,1, 200,1) selbst ergänzen.

Fehler 2: das Ergebnis der Funktion als Erwartung (Zeilen 5 und 6)

erwartet = zustand(85) und dann assert zustand(85) == erwartet vergleicht die Funktion mit sich selbst. Dieser Test besteht immer, auch wenn zustand(85) falsch ist. Er ist die gefährlichste Sorte, weil er wie ein Test aussieht und etwas prüft, das nie scheitern kann. Das Erwartete rechnest du aus der Spezifikation von Hand: assert zustand(85) == "warnung".

Fehler 3: assert mit Klammern (Zeile 7)

Die Klammern um Bedingung und Meldung machen ein Tupel daraus, und ein nicht leeres Tupel ist immer wahr. Python meldet höchstens eine Warnung („assertion is always true“), dann geht es weiter: Der Test prüft nichts, auch wenn zustand(250) falsch wäre. Lösung: assert zustand(250) == "sensorfehler", "über 200 °C ist ein Sensorfehler", ohne Klammern um das Ganze.

Die KI-Tests gegen die fehlerhafte Funktion

Die KI-Funktion hat den Fehler bei 85 und den Sensorfehler vergessen. Die Tests sind trotzdem alle grün (Python warnt höchstens vor dem assert mit Klammern).

def zustand(t):
    if t < 70:
        return "normal"
    elif t < 85:
        return "warnung"
    else:
        return "abschalten"

def test_zustand():
    assert zustand(20) == "normal"
    assert zustand(75) == "warnung"
    assert zustand(90) == "abschalten"
    erwartet = zustand(85)
    assert zustand(85) == erwartet
    assert (zustand(250) == "sensorfehler", "über 200 °C ist ein Sensorfehler")
    print("Alle Tests bestanden")

test_zustand()

Merke

Bei KI-Tests prüfst du immer vier Dinge: Sind die Grenzen von beiden Seiten dabei? Stammt jedes erwartete Ergebnis aus der Spezifikation und nicht aus der Funktion selbst? Steht jedes assert ohne Klammern um das Ganze? Und: Findet der Test einen Fehler, den du absichtlich einbaust? Das Letzte machst du, indem du die Funktion kaputt machst und beobachtest, ob ein Test rot wird. Grüne Tests sind erst dann etwas wert, wenn sie auch rot werden können.

Typische Fehlermeldungen

Beim Testen begegnen dir Fehler mit Meldung und solche ganz ohne. Jedes Beispiel lässt sich ausführen: Schau dir die echte Meldung an und lies sie von unten nach oben (zuerst die letzte Zeile).

AssertionError mit Meldung: der Test ist gescheitert

Meldung: AssertionError: 36 km/h müssen 10 m/s sein. Das ist keine Störung, sondern das Ziel: Der Test hat einen Fehler gefunden. Die Meldung stammt von dir. Der Traceback zeigt die Zeile des assert, nicht die des Fehlers in der Funktion: Dort steht * 3.6 statt / 3.6. Suche mit Hypothese, print und „Schritt für Schritt“.

AssertionError ohne Meldung

Meldung: nur AssertionError, ohne Text. Du siehst die Zeile des gescheiterten assert (Zeile 10, der Test für 85), aber nicht, welche Werte erwartet und bekommen wurden. Mit einer Meldung hinter dem Komma (assert ..., f"85: bekommen {zustand(85)}") sparst du dir das Suchen. Bei vielen Fällen gehört der Wert in die Meldung.

SyntaxError: ein Gleichheitszeichen statt zwei

Meldung: SyntaxError in der Zeile mit dem assert, meist mit dem Tipp Maybe you meant '==' instead of '='?. Ein Syntaxfehler verhindert, dass das Programm überhaupt startet: Keine einzige Zeile läuft, auch das print nicht. Vergleichen heißt ==, zuweisen heißt =.

NameError: Tippfehler im Test

Meldung: NameError: name 'zustnd' is not defined. Der Test selbst ist kaputt, nicht das Programm: Ein Buchstabe fehlt im Namen. Die Meldung nennt den Namen, den Python nicht kennt, und schlägt oft den ähnlichen richtigen vor („Did you mean“). Lies den Traceback von unten: Die Stelle zeigt die Zeile in test_zustand. Das ist ein Laufzeitfehler: Er tritt erst auf, wenn die Testfunktion läuft.

TypeError: Text und Zahl zusammengeklebt

Meldung: TypeError: can only concatenate str (not "float") to str. Das Pluszeichen klebt nur Text an Text. Die Meldung nennt die beiden Typen: links ein str (Text), rechts ein float (Kommazahl). Lösung: str(wert) oder ein f-String (V03): f"{sensor}: {wert} °C".

Grün, aber falsch: assert mit Klammern prüft nichts

Ausgabe: „Test bestanden, aber verdopple(5) ist 7“, höchstens mit der Warnung „assertion is always true, perhaps remove parentheses?“. Python hat keinen Fehler gemeldet: Die Klammern machen ein Tupel, das nie falsch ist. Ein solcher Test beruhigt dich, ohne etwas zu prüfen. Schreibe assert verdopple(5) == 10, "5 verdoppelt ist 10" ohne Klammern um das Ganze, und der Test schlägt an.

PAP zeichnen: Temperaturampel

Lagertemperatur als PAP

Zeichne den Programmablaufplan der Lagertemperatur-Ampel: Das Programm liest die Temperatur t in °C (Kommazahl) ein und gibt genau eines der drei Wörter aus: "normal" unter 70 °C, "warnung" von 70 °C bis einschließlich 85 °C, sonst "abschalten". Der Text einer Ausgabe steht in Anführungszeichen. Der Plan hat zwei Rauten hintereinander. Die Prüfung testet deinen Plan mit den Werten aus der Lerneinheit, auch an den Grenzen 70 und 85: Genau dort entscheidet das Zeichen in der Raute, < oder <=.

  1. Nach der Eingabe kommt die erste Verzweigung mit der Bedingung t < 70. Im Weg „ja“ steht die Ausgabe "normal" (mit Anführungszeichen).
  2. Im Weg „nein“ steht die zweite Verzweigung mit t <= 85: „ja“ gibt "warnung" aus, „nein“ gibt "abschalten" aus. Zwei Rauten, drei Ausgaben.
  3. Achte auf das Gleichheitszeichen in der zweiten Raute: Die Grenze 85 gehört noch zur Warnung. Du kannst ≤ oder <= schreiben. Das ist genau der Test an der Grenze.

Fehler finden: stärkste Bremsung mit dem Visualisierer

Die Funktion staerkste_bremsung(werte) soll aus einer Beschleunigungsreihe (m/s²) den kleinsten Wert liefern, also die stärkste Verzögerung. Beim Anfahren ohne Bremsung gibt sie aber 0.0 statt 0.2 aus. Es gibt keinen Traceback: ein Logikfehler. Gehe den Zyklus durch: Hypothese (wo könnte es liegen?), Beobachten (drück „Schritt für Schritt“ und achte auf kleinster), Korrigieren (eine Änderung), Test erneut (Prüfen).

Ausgabe genau so:
0.2
  1. Hypothese: Die Suche nach dem kleinsten Wert braucht einen Startwert. Welcher Wert steht am Anfang in kleinster, und ist er für jede Liste sinnvoll? Beobachte im Visualisierer, wie kleinster sich entwickelt, wenn alle Werte positiv sind.

Knobelaufgabe: Schutzfunktion mit höchstens sechs Testfällen

Eine Maschine darf nur starten, wenn die Schutztür geschlossen ist und der Not-Halt nicht gedrückt ist und (die Spindel steht oder der Bediener hat den Anlauf quittiert). Die Funktion schutz_ok(tuer_zu, notaus, spindel_steht, quittiert) setzt das mit Wahrheitswerten um (V04). Vier Wahrheitswerte ergeben 16 Kombinationen, und du hast nur höchstens sechs Testfälle. Die Prüfung lässt deine Liste gegen sieben fehlerhafte Varianten laufen, in denen je ein and, or oder not falsch ist. Wähle die Fälle so, dass jede Variante scheitert. Fünf reichen.

Eintrag in faelle:
(tuer_zu, notaus, spindel_steht, quittiert, erwartet)
(True, False, True, False, True)
  1. Jede Variante hat eine Kombination, bei der sie anders antwortet als die richtige Regel. Überlege für jede Bedingung: Welcher Fall zeigt, dass sie gebraucht wird? Die Tür: Alles andere passt, nur die Tür ist offen, erwartet False. Der Not-Halt: nur er ist gedrückt, erwartet False.
  2. Die Klammer (spindel_steht or quittiert) brauchst du in drei Fällen: nur die Spindel steht (True), nur quittiert (True), keines von beiden (False). Mit dem ersten allein findest du die Variante „nur Quittierung“ und „und statt oder“ noch nicht.
  3. Eine Lösung mit fünf Fällen: der Starterfall plus (True, False, False, True, True), (True, False, False, False, False), (False, False, True, False, False) und (True, True, True, False, False).
