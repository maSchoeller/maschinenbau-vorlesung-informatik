Testen & Debuggen: prüfen, bevor du vertraust

Ab jetzt darf die KI Code erzeugen. Dann ist dein Beitrag das Prüfen, und das Prüfen beginnt vor dem Generieren: Du schreibst die Testfälle von Hand, an den Stellen, an denen Fehler wirklich sitzen: an den Grenzen. Und wenn ein Test scheitert, findest du den Fehler mit Methode statt mit Raten.

Nach dieser Lerneinheit kannst du:

  • einen Test als Vergleich von erwartet gegen tatsächlich erklären und mit assert schreiben,
  • Testfälle systematisch ableiten: je Bereich ein Vertreter, an jeder Grenze beide Seiten,
  • die drei Fehlerarten unterscheiden: Syntaxfehler, Laufzeitfehler und Logikfehler,
  • einen Traceback über mehrere Funktionsaufrufe von unten nach oben lesen,
  • Fehler mit dem Zyklus Hypothese, Beobachten, Korrigieren, Test erneut finden, mit print und mit dem Schritt-für-Schritt-Visualisierer, und wissen, was ein Debugger in VS Code tut.

Das Schreiben der Tests übst du danach im Programmierlabor. Funktionen (V07), Listen und Tupel (V08), try/except (V09) und das Arbeiten mit der KI (V10, V11) setzen wir voraus.

1 Warum?

Ein Lager in einer Förderanlage meldet seine Temperatur. Die Spezifikation aus dem Lastenheft: unter 70 °C normal, von 70 °C bis einschließlich 85 °C Warnung, über 85 °C abschalten. Messwerte unter −40 °C oder über 200 °C sind Sensorfehler, etwa ein Kabelbruch.

Die KI liefert in Sekunden

Du lässt die KI die Funktion schreiben, so wie in V11 gelernt. Sie antwortet sofort, der Code sieht sauber aus, und die ersten Werte, die du ausprobierst, passen: 20 °C normal, 75 °C Warnung, 90 °C abschalten. Würdest du freigeben?

Selbst sehen: drei Werte, drei Treffer

Der Code ist die Antwort der KI (ohne den Sensorfehler-Zweig, den hast du im Prompt vergessen). Die Schleife unten läuft über eine Liste (V08) und ruft die Funktion für jeden Wert auf. Führe sie aus.

def zustand_ki(t):
    if t < 70:
        return "normal"
    elif t < 85:
        return "warnung"
    else:
        return "abschalten"

for t in [20, 75, 90]:
    print(t, "°C:", zustand_ki(t))

Alle drei Werte stimmen. Was liefert zustand_ki(85), genau auf der Grenze?

„abschalten“. Die KI hat t < 85 geschrieben, die Spezifikation sagt aber „bis einschließlich 85“, also t <= 85. Bei 84,9 °C ist alles gut, bei 85,0 °C schaltet die Anlage ab, obwohl nur Warnung vorgesehen ist. Kein Traceback, keine Fehlermeldung: ein Logikfehler. Er fällt nur auf, wenn du genau diesen Wert testest. Probiere es aus: Ändere die Liste auf [85].

Genau 85 °C

Messwerte sind oft gerundet, und 85,0 kommt in der Praxis ständig vor. Die Anlage schaltet ohne Not ab, und niemand versteht, warum, denn der Code „funktioniert“. Dieser eine Fehler ist typisch für alles, was die KI schreibt: Sie liefert den Normalfall richtig und patzt an den Kanten. Nur ein Test an der Grenze findet ihn, und diesen Test musst du schreiben, am besten bevor du den Code überhaupt gesehen hast. Heute lernst du, wie.

Wissens-Ampel für V12

  • Im KopfEin Test ist erwartet gegen tatsächlich. Testfälle kommen aus der Spezifikation, nicht aus dem Code: je Bereich ein Wert, an jeder Grenze beide Seiten. Ein bestandener Test beweist keine Fehlerfreiheit. Der Traceback wird von unten gelesen, und ein Logikfehler hat keinen Traceback.
  • Lesen & erkennenassert bedingung, "Meldung", AssertionError, Testfunktionen def test_...():, Testfälle als Liste von Tupeln, except AssertionError as fehler, die Oberfläche des VS-Code-Debuggers (Haltepunkt, Variablenfenster, Schritt über und hinein).
  • DelegierenTest-Gerüste wie pytest und die Messung, wie viel Code die Tests berühren (Abdeckung), übernehmen Werkzeuge. Auch Vorschläge für Testfälle darf die KI machen, aber du prüfst, ob die Grenzen dabei sind. Du musst wissen, dass es sie gibt.
Warum muss ich das wissen?

Phase 2 dieses Kurses heißt: Die KI erzeugt, du prüfst. Das Prüfen ist das eigentliche Ingenieurhandwerk, denn die Haftung liegt bei dir, nicht bei der KI. Wer die Tests nach dem Code schreibt, schreibt unbewusst Tests, die der Code besteht. Wer sie vorher aus der Spezifikation ableitet, prüft wirklich. Und lässt du die KI die Tests schreiben, bekommst du fast immer nur Normalfälle. In der Klausur erscheint das als „Welche Testfälle prüfen die Grenzen?“, als Traceback zum Lesen oder als Code mit einem versteckten Fehler.

2 Theorie

Erklärvideo (ca. 3 Min)

Ein Test: erwartet gegen tatsächlich

Bisher hast du Programme getestet, indem du sie ausgeführt und das Ergebnis angeschaut hast. Das ist ein Test mit dem Auge, und er hat zwei Schwächen: Er kostet jedes Mal Zeit, und du siehst nur, was du erwartest zu sehen. Ein richtiger Test legt vorher fest, was herauskommen soll (erwartet), führt das Programm aus (tatsächlich) und vergleicht beides von selbst. Das Erwartete steht dabei nie im Programm, sondern in der Spezifikation: Du rechnest es vorher von Hand aus.

def zustand(t):
    if t < -40 or t > 200:
        return "sensorfehler"
    if t < 70:
        return "normal"
    elif t <= 85:
        return "warnung"
    else:
        return "abschalten"

erwartet = "warnung"             # aus der Spezifikation, von Hand bestimmt
tatsaechlich = zustand(85)       # was das Programm liefert
print("erwartet:", erwartet, "| tatsächlich:", tatsaechlich)
print(erwartet == tatsaechlich)

assert: der Computer vergleicht für dich

Python hat dafür ein eigenes Wort. assert stellt eine Behauptung auf: assert bedingung. Ist die Bedingung wahr, passiert nichts, das Programm läuft still weiter. Ist sie falsch, bricht Python ab und löst einen AssertionError aus. Hinter ein Komma kannst du eine Meldung schreiben, die im Fehlerfall erscheint: assert bedingung, "Meldung". Schreibe die Meldung so, dass sie dir in drei Wochen noch sagt, was los ist: Wert, erwartet, bekommen.

def kmh_in_ms(v):
    return v * 3.6        # der Fehler steckt hier, die KI hat mal statt durch geschrieben

assert kmh_in_ms(0) == 0.0
print("Der erste Test schweigt, denn 0 mal 3,6 ist auch 0.")
assert kmh_in_ms(36) == 10.0, "36 km/h müssen 10 m/s sein"
print("Diese Zeile erreicht Python nicht mehr.")

Der erste assert besteht, der zweite scheitert, und die Meldung steht im Traceback. Der Fehler wäre beim Ausprobieren mit 0 nicht aufgefallen: ein Beispiel dafür, dass welche Werte du testest, entscheidend ist. Bei Kommazahlen vergleichst du nicht mit ==, sondern mit math.isclose (V03), weil 0.1 + 0.2 == 0.3 falsch ist: assert math.isclose(kmh_in_ms(100), 27.7778, rel_tol=1e-4).

Achtung

Ein bestandener Test beweist nicht, dass das Programm richtig ist, nur, dass es für diese Werte richtig ist. Der Test findet Fehler, er garantiert keine Fehlerfreiheit. Darum kommt es darauf an, welche Werte du wählst. Und: Nimm als erwarteten Wert nie das, was die Funktion selbst liefert („das Ergebnis steht ja auf dem Bildschirm“). Dann prüft der Test nur, ob die Funktion sich selbst gleicht, und besteht immer.

Testfunktionen und Testfälle als Liste

Mehrere assert-Zeilen packst du in eine Funktion, deren Name mit test_ beginnt, und rufst sie selbst auf. So kannst du sie in ein Programm einbauen, immer wieder ausführen und mit einer Zeile alle Tests starten. Reicht eine Zeile je Fall nicht mehr, schreibst du die Testfälle als Liste von Tupeln (V08): jedes Tupel ist ein Paar aus Eingabe und erwartetem Ergebnis. Eine Schleife geht sie durch. Mit for t, erwartet in faelle: wird jedes Tupel in zwei Namen ausgepackt, wie bei items() in V08.

def zustand(t):
    if t < -40 or t > 200:
        return "sensorfehler"
    if t < 70:
        return "normal"
    elif t <= 85:
        return "warnung"
    else:
        return "abschalten"

def test_zustand():
    faelle = [
        (20, "normal"),
        (69.9, "normal"),
        (70, "warnung"),
        (85, "warnung"),
        (85.1, "abschalten"),
        (-40.1, "sensorfehler"),
    ]
    for t, erwartet in faelle:
        tatsaechlich = zustand(t)
        assert tatsaechlich == erwartet, f"{t} °C: erwartet {erwartet}, bekommen {tatsaechlich}"
    print(len(faelle), "Testfälle bestanden")

test_zustand()

Im Fehlerfall bricht der erste gescheiterte assert alles ab. Willst du alle Ergebnisse sehen, fängst du den AssertionError mit try/except (V09). Neu ist das kleine Wort as: except AssertionError as fehler: gibt der Ausnahme den Namen fehler, und print(fehler) zeigt deine Meldung aus dem assert.

def zustand_ki(t):
    if t < 70:
        return "normal"
    elif t < 85:
        return "warnung"
    else:
        return "abschalten"

fehlgeschlagen = 0
for t, erwartet in [(20, "normal"), (70, "warnung"), (85, "warnung"), (90, "abschalten")]:
    try:
        assert zustand_ki(t) == erwartet, f"{t} °C: erwartet {erwartet}, bekommen {zustand_ki(t)}"
    except AssertionError as fehler:
        fehlgeschlagen = fehlgeschlagen + 1
        print("GESCHEITERT:", fehler)
print(fehlgeschlagen, "von 4 Tests gescheitert")

Testfälle systematisch: Bereiche und Grenzen

Welche Werte testest du? Nicht „irgendwelche“, sondern nach zwei Regeln. Erstens: Bereiche. Die Spezifikation zerlegt die Eingaben in Bereiche, in denen sich die Funktion gleich verhält. Hier sind es fünf: Sensorfehler unten, normal, Warnung, abschalten, Sensorfehler oben. Ein Vertreter je Bereich genügt, denn wenn die Funktion bei 20 °C richtig arbeitet, tut sie es auch bei 21 °C (diese Bereiche heißen Äquivalenzklassen). Zweitens: Grenzen. Fehler sitzen fast immer an den Kanten, weil man dort zwischen < und <= entscheiden muss. Darum testest du jede Grenze von beiden Seiten: den letzten Wert, der noch drin ist, und den ersten, der schon draußen ist. Hier: 69,9 und 70, 85 und 85,1, −40,1 und −40, 200 und 200,1. Dazu kommen Sonderfälle wie 0, negative Zahlen oder eine leere Liste.

Testpunkte setzen: wie viele Fehler findest du?

Setze Testpunkte (Klick in den Zahlenstrahl oder einen Wert eintippen). Rechts siehst du Mutanten: Das sind Kopien der Funktion mit je einem absichtlich eingebauten Fehler, zum Beispiel < statt <=. Ein guter Test findet jeden Mutanten, weil mindestens ein Testpunkt ein anderes Ergebnis bekommt als erwartet. Probiere zuerst „Nur typische Werte“ (die Mitte jedes Bereichs), dann „Die 9 Tests aus dem Beispiel“, dann baue dir selbst die kleinste Menge, die alle acht findet.

Beobachtung: Mit den typischen Werten aus der Mitte jedes Bereichs findest du nur wenige Mutanten, vor allem die groben. Die feinen Fehler an den Grenzen (< statt <=) findet nur ein Testpunkt genau auf der Grenze, und für verschobene Grenzen einer knapp dahinter. Mutanten sind die Idee, mit der man auch in der Industrie die Qualität von Tests prüft. Im Labor machst du genau das: Deine Tests laufen gegen die richtige Funktion und gegen mehrere fehlerhafte.

Merke

Testfälle leitest du aus der Spezifikation ab, nicht aus dem Code, und schreibst sie vor dem Generieren. Je Bereich ein typischer Wert, an jeder Grenze beide Seiten (der letzte Wert drinnen, der erste draußen), dazu Sonderfälle. Das erwartete Ergebnis rechnest du von Hand. Ein Test, der alle Mutanten findet, ist ein guter Test.

Aus dem Programmablaufplan werden Testfälle

Den Programmablaufplan (V05) hast du als Bauplan für den Prompt benutzt. Er ist auch der Bauplan für die Tests: Jeder Weg vom Start zum Ende ist ein Pfad, und jeder Pfad braucht mindestens einen Testfall. Jede Raute ist eine Grenze, und an jeder Raute testest du beide Seiten. Die Funktion zustand hat drei Rauten hintereinander und vier Wege.

Der PAP der Funktion zustand und seine Testfälle

Gib einen Wert für t ein oder klicke einen Wert in der Tabelle an: Der Plan zeigt den Pfad durch die Rauten. Die Tabelle ist die Ausbeute des Plans: je Pfad ein typischer Wert, dazu die Grenzwerte an den Rauten. Die neun Tests aus dem Beispiel im Labor sind eine Auswahl daraus.

Fehlerarten: Syntax, Laufzeit, Logik

Es gibt drei Arten von Fehlern, und sie verhalten sich völlig verschieden. Ein Syntaxfehler verstößt gegen die Schreibregeln: Python meldet ihn, bevor das Programm anläuft, mit Zeilennummer. Ein Laufzeitfehler tritt erst auf, wenn die Zeile drankommt: Das Programm bricht ab und druckt einen Traceback. Ein Logikfehler ist ein Denkfehler: Das Programm läuft ohne Meldung durch und liefert ein falsches Ergebnis. Die ersten beiden meldet Python von selbst. Den dritten findet nur ein Test oder dein Kopf, und er ist der gefährlichste, denn er sieht aus wie ein Erfolg. Der KI-Fehler aus dem Hook gehört dazu.

Welche Fehlerart ist das?

Sechs kurze Beispiele. Entscheide für jedes, ob Python den Fehler vor dem Start meldet, beim Laufen mit Traceback oder gar nicht.

Einen Traceback lesen: von unten nach oben

Aus V09 weißt du: Der Traceback wird von unten nach oben gelesen. In echten Programmen ruft eine Funktion die nächste auf, und der Traceback zeigt die ganze Kette. Ganz unten steht die Fehlerart mit der Meldung: das Was. Die Zeile darüber ist die Fehlerstelle: das Wo. Jeder Eintrag weiter oben ist der Aufrufer, der die Funktion darunter gestartet hat: das Wie kam es dazu. Ganz oben steht das Hauptprogramm, <module>. Die Ursache liegt oft nicht in der untersten Zeile, sondern weiter oben oder in den Daten.

Mehrstufiger Traceback, Zeile für Zeile

Drei Beispiele mit mehreren Funktionen. Gehe mit „Nächste Zeile lesen“ von unten nach oben und beobachte, welche Codezeile jeweils leuchtet. Im dritten Beispiel scheitert ein assert: Achte darauf, welche Funktion im Traceback fehlt.

Debuggen: mit Methode statt mit Raten

Ein Test hat dir gesagt: Da ist ein Fehler. Das Wort Debuggen (englisch bug, der Käfer) meint die Suche nach der Ursache. Wildes Ändern („vielleicht hilft ein + 1“) macht Programme schlechter. Besser ist ein Kreislauf: Test scheitert, Hypothese aufstellen (eine prüfbare Vermutung, was die Ursache ist), Beobachten (sichtbar machen, was wirklich passiert), Korrigieren (eine Sache ändern), Test erneut (alle Tests, nicht nur den einen). Bestehen sie nicht alle, beginnt der Kreislauf von vorn.

Der Debug-Zyklus am KI-Fehler

Gehe die fünf Schritte durch, am Beispiel des Fehlers an der Grenze 85. Beachte, was jeweils ausgetauscht wird: Die Beobachtung macht aus der Vermutung ein Wissen.

Beobachten: print und Schritt für Schritt

Zum Beobachten gibt es zwei einfache Werkzeuge. Mit print lässt du dir an der verdächtigen Stelle Werte ausgeben (die zweite Variable ist oft die wichtigste: nicht nur t, sondern auch das Ergebnis der Bedingung). Und der Knopf „Schritt für Schritt“ unter jedem Codefeld in diesem Kurs ist ein kleiner Debugger: Er führt dein Programm Zeile für Zeile aus und zeigt, welche Zeile als Nächstes dran ist, was in den Variablen steht und was ausgegeben wurde. Probiere ihn gleich an diesem Code, und beachte, welche Zeile bei 85 übersprungen wird.

def zustand_ki(t):
    if t < 70:
        return "normal"
    elif t < 85:
        return "warnung"
    return "abschalten"

t = 85
print("t =", t, "| t < 85 ist", t < 85)
print(zustand_ki(t))

Der Debugger in VS Code

In der Entwicklungsumgebung (VS Code, in Codespaces aus V11) gibt es denselben Gedanken in groß: den Debugger. Du setzt einen Haltepunkt (roter Punkt am Zeilenrand), startest das Programm im Debug-Modus, und es hält dort an. Du siehst im Fenster Variablen alle Werte, in der Aufrufliste die Kette der Funktionen, und gehst mit Schritt über (die Zeile ganz ausführen, auch einen Funktionsaufruf in einem Schritt) oder Schritt hinein (in die aufgerufene Funktion springen) weiter. Du musst ihn nicht bedienen können, aber erkennen, was er zeigt. Das Schema:

Der Debugger als Schema zum Durchklicken

Das Programm ist die KI-Version mit dem Fehler. Der Haltepunkt steht in Zeile 10 (Klick auf den Rand setzt oder löscht Haltepunkte). Starte das Debuggen, dann gehe mit „Schritt hinein“ in die Funktion. Beobachte das Fenster „Variablen“ und die Aufrufliste, und finde beim zweiten Messwert die Stelle, an der es schiefgeht. Probiere auch „Schritt über“ (der ganze Aufruf in einem Schritt) und „Schritt heraus“.

Beobachtung: Mit „Schritt über“ siehst du nur das Ergebnis, mit „Schritt hinein“ die Entscheidungen in der Funktion. Der Fehler zeigte sich erst im zweiten Durchlauf, bei t = 85.0, in Zeile 4. Ein Haltepunkt mit Bedingung (w == 85.0) hätte dich sofort dorthin gebracht, aber das ist Stoff für den Deep Dive.

Merke

assert bedingung, "Meldung" schweigt, wenn die Bedingung stimmt, und löst sonst AssertionError aus. Testfälle: je Bereich ein Vertreter, an jeder Grenze beide Seiten, als Liste von Tupeln mit Schleife. Syntax- und Laufzeitfehler meldet Python, einen Logikfehler findet nur ein Test. Der Traceback wird von unten nach oben gelesen: erst Fehlerart, dann Stelle, dann Aufrufer. Debuggen heißt Hypothese, Beobachten, Korrigieren, Test erneut.

3 Ausprobieren

Python läuft direkt hier im Browser. Jeder Codeblock hat einen Editor: Du kannst ihn ändern, ausführen, zurücksetzen und mit „Schritt für Schritt“ verfolgen. Erst tippen, was herauskommt, dann ausführen. Das Tippen ist der Lernmoment. Mit „Zurücksetzen“ holst du das Original (Strg+Enter führt aus).

assert schweigt

Was gibt das Programm aus?

Nur „Ende“. Beide Behauptungen sind wahr, assert tut dann gar nichts: Es druckt keinen Erfolg, es meldet sich nur im Fehlerfall. Darum steht bei Tests oft am Ende ein print("Alle Tests bestanden"). Ändere die zweite Behauptung zu len("ab") == 3 und lies den Fehler.
assert 2 + 2 == 4
assert len("ab") == 2, "ab hat zwei Zeichen"
print("Ende")

Die Meldung im Traceback

Was steht in der letzten Zeile des Tracebacks?

Die Meldung hinter dem Komma erscheint hinter dem Doppelpunkt. Der Wert von kmh_in_ms(100) ist 360.0 statt 27.78: Die Funktion rechnet mal 3,6 statt durch 3,6. Mit der Meldung siehst du sofort, welcher Test gescheitert ist. Repariere die Funktion und führe nochmal aus: Der Test schweigt. Beachte math.isclose: Bei Kommazahlen vergleichst du mit einer Toleranz.
import math

def kmh_in_ms(v):
    return v * 3.6

assert math.isclose(kmh_in_ms(100), 27.7778, rel_tol=1e-4), "100 km/h müssen etwa 27,8 m/s sein"
print("bestanden")

Testfälle als Liste von Tupeln

Wie viele der vier Testfälle scheitern?

1: Der Fall (50, 1.60) scheitert, weil die Funktion mit < 50 die Grenze ausschließt und bei 50 das Porto der nächsten Stufe liefert (2.75). Die anderen drei stimmen. Das Muster mit einem Zähler statt assert zeigt dir alle gescheiterten Fälle statt nur den ersten. Setze in Zeile 4 das Gleichheitszeichen dazu (<=) und alle vier bestehen.
def porto(gramm):
    if gramm <= 20:
        return 0.95
    elif gramm < 50:
        return 1.60
    return 2.75

faelle = [(20, 0.95), (21, 1.60), (50, 1.60), (51, 2.75)]
gescheitert = 0
for gramm, erwartet in faelle:
    if porto(gramm) != erwartet:
        gescheitert = gescheitert + 1
        print("Fall", gramm, "g: erwartet", erwartet, "bekommen", porto(gramm))
print(gescheitert, "von", len(faelle), "Fällen gescheitert")

except AssertionError as fehler

Was gibt das Programm aus?

9 ** 0.5 ist 3.0, nicht 4: Der assert scheitert, Python springt in den except-Block, und fehler enthält die Meldung „Wurzel falsch“. Das Programm läuft danach weiter, es bricht nicht ab. In einem Testprogramm ist das nützlich, weil du alle Ergebnisse siehst. In Anwendungen fängt man AssertionErrors nicht.
try:
    assert 9 ** 0.5 == 4, "Wurzel falsch"
    print("Test bestanden")
except AssertionError as fehler:
    print("Test gescheitert:", fehler)
print("weiter")

Einen Traceback lesen

In welcher Funktion und welcher Zeile tritt der Fehler auf?

Die unterste Zeile des Tracebacks zeigt die Fehlerstelle: mittelwert, Zeile 2, ZeroDivisionError. auswerten und das Hauptprogramm stehen darüber, weil sie mittelwert aufgerufen haben. Die Ursache ist aber eine leere Liste, die weiter oben übergeben wurde. Ergänze in mittelwert eine Prüfung für die leere Liste.
def mittelwert(werte):
    return sum(werte) / len(werte)

def auswerten(messreihen):
    for reihe in messreihen:
        print(mittelwert(reihe))

auswerten([[20, 22], []])

Den Fehler mit print und „Schritt für Schritt“ finden

Der Mittelwert von 10, 20 und 30 müsste 20.0 sein. Was gibt das Programm aus?

16.666666666666668: range(1, len(werte)) beginnt bei Index 1, das erste Element (10) wird übersprungen. Es steht 50 in der Summe statt 60, geteilt durch 3. Ein Logikfehler ohne Traceback. Finde ihn mit „Schritt für Schritt“: Beobachte i und summe in jedem Durchlauf. Hypothese, Beobachten, Korrigieren: range(len(werte)).
def mittelwert(werte):
    summe = 0
    for i in range(1, len(werte)):
        summe = summe + werte[i]
    return summe / len(werte)

print(mittelwert([10, 20, 30]))

4 Selbstcheck

Acht Quizaufgaben im Stil der Probeklausur (22 Punkte) und eine Code-Schreib-Aufgabe (6 Punkte, T9). Plane etwa 15 Minuten für das Quiz und 12 Minuten für T9 ein, ohne Hilfsmittel. Quiz-Punkte gibt es für den ersten Versuch; danach darfst du es nochmal probieren.

T1 · assert und except von Hand2 Punkte
Was gibt das Programm aus?
try:
    assert 2 + 2 == 5, "Rechenfehler"
    print("A")
except AssertionError as fehler:
    print("B", fehler)
2 + 2 == 5 ist falsch, der assert löst einen AssertionError mit der Meldung „Rechenfehler“ aus. Das print("A") wird übersprungen, der except-Block läuft, fehler enthält die Meldung. Ausgabe: B Rechenfehler.
T2 · Was assert tut2 Punkte
Was geschieht bei assert x > 0, "x muss positiv sein", wenn x den Wert 5 hat?
  • Python gibt „x muss positiv sein“ aus.
  • Nichts: Die Behauptung ist wahr, das Programm läuft still weiter.
  • Python löst einen AssertionError aus.
  • Python setzt x auf 0.
Die Meldung erscheint nur, wenn die Bedingung falsch ist. Ist sie wahr, schweigt assert. Darum bedeutet „keine Ausgabe“ bei Tests: alles in Ordnung.
T3 · Grenzwerte wählen2 Punkte
Die Funktion ist_gut(d) soll für Durchmesser von 24,98 mm bis einschließlich 25,02 mm True liefern, sonst False. Welche Testwerte prüfen die Grenzen am besten?
  • 25,00 und 25,01
  • 24,97 und 24,98 sowie 25,02 und 25,03
  • 24,0 und 25,0 und 26,0
  • 0 und 100
An jeder der beiden Grenzen testest du beide Seiten: 24,98 (noch gut) und 24,97 (schon zu klein), 25,02 (noch gut) und 25,03 (schon zu groß). Werte aus der Mitte (25,00) finden Fehler an der Grenze nicht, und weit entfernte Werte (0 und 100) auch nicht.
T4 · Testfälle von Hand durchrechnen3 Punkte
Was gibt das Programm aus?
def porto(g):
    if g <= 20:
        return 0.95
    elif g <= 50:
        return 1.60
    return 2.75

faelle = [(20, 0.95), (21, 1.60), (50, 1.60), (51, 1.60)]
fehler = 0
for g, soll in faelle:
    if porto(g) != soll:
        fehler = fehler + 1
print(fehler)
Fall 1: porto(20) ist 0.95, passt. Fall 2: 21 g gehört zu <= 50, 1.60, passt. Fall 3: 50 g, 1.60, passt. Fall 4: 51 g ist größer als 50, also 2.75, erwartet war 1.60: gescheitert. Ausgabe: 1. Der Testfall 4 hat den falschen erwarteten Wert: Auch Tests können Fehler haben.
T5 · Aussagen (mehrere richtig)4 Punkte
Welche Aussagen sind richtig? Alle richtigen ankreuzen.
  • Ein bestandener Test beweist nicht, dass das Programm fehlerfrei ist.
  • Ein Logikfehler erzeugt immer einen Traceback.
  • Ein Syntaxfehler wird gemeldet, bevor das Programm läuft.
  • Es genügt, je Bereich einen Wert aus der Mitte zu testen.
  • Ein Test, der als Erwartung das Ergebnis der getesteten Funktion selbst nimmt, prüft nichts.
Ein Logikfehler läuft ohne Meldung durch. Aus der Mitte der Bereiche findest du nur grobe Fehler, die Fehler an den Grenzen übersiehst du. Die drei richtigen Aussagen sind die Kernsätze der Lerneinheit.
T6 · assert in der Schleife3 Punkte
Was gibt das Programm aus?
def pruefe(t):
    assert t >= 0, "negativ"
    return t * 2

werte = [3, -1, 4]
summe = 0
for w in werte:
    try:
        summe = summe + pruefe(w)
    except AssertionError:
        summe = summe - 1
print(summe)
w = 3: pruefe(3) ist 6, summe 6. w = −1: der assert scheitert, Python springt in den except-Block, summe = 6 − 1 = 5 (die Addition hat nicht stattgefunden). w = 4: 8, summe 13. Ausgabe: 13.
T7 · Traceback lesen3 Punkte
Python meldet:
Traceback (most recent call last):
  File "auswertung.py", line 14, in <module>
    ergebnis = mittelwert(daten)
  File "auswertung.py", line 8, in mittelwert
    return summe / len(werte)
ZeroDivisionError: division by zero
Wo ist der Fehler aufgetreten, und was ist die wahrscheinlichste Ursache?
  • In Zeile 14 im Hauptprogramm: Die Funktion mittelwert gibt es nicht.
  • In Zeile 8 in mittelwert: len(werte) ist 0, die Liste war leer.
  • In Zeile 8: summe ist 0, deshalb ist das Ergebnis 0.
  • Es ist ein Syntaxfehler in Zeile 14.
Die Fehlerstelle ist der unterste Eintrag: Zeile 8 in mittelwert. Geteilt wird durch len(werte), und eine Division durch null entsteht nur, wenn die Liste leer ist. Zeile 14 ist der Aufrufer, nicht die Fehlerstelle. Die Ursache liegt in den Daten oder in der fehlenden Prüfung für die leere Liste.
T8 · KI-Tests freigeben?3 Punkte
Du hast der KI die Spezifikation der Lagertemperatur (Bereiche 70 und 85, Sensorfehler unter −40 und über 200) gegeben und Tests verlangt. Sie liefert:
def test_zustand():

    assert zustand(75) == "warnung"
    assert zustand(90) == "abschalten"
Würdest du die Tests freigeben?
  • Ja, alle drei Bereiche sind abgedeckt.
  • Nein, es fehlen die Grenzwerte (70, 85 und Nachbarwerte) und die Sensorfehler.
  • Nein, assert darf nicht in einer Funktion stehen.
  • Nein, die Tests müssen mit print arbeiten.
Die drei Werte stehen in der Mitte der Bereiche. Der Fehler < statt <= bei 85 würde alle drei Tests bestehen. Gute Tests prüfen 69,9 und 70, 85 und 85,1, und die Sensorfehler. assert in Testfunktionen ist üblich.

Code schreiben im Klausurstil

Wie in der Klausur: erst von Hand schreiben, ohne Ausführen und ohne Auto-Vervollständigung. Dann abgeben, die Tests laufen lassen und dich selbst nach dem Punkteschema bewerten. Richtzeit 12 Minuten. Die Funktion gebuehr steht schon im Editor, du schreibst die Testfunktion darunter. Die Prüfung lässt deine Tests gegen die richtige Funktion und gegen mehrere fehlerhafte laufen: Gute Tests bestehen bei der richtigen und scheitern bei jeder fehlerhaften.

T9 · Testfälle für die Versandgebühr6 Punkte

Ein Online-Händler berechnet die Versandgebühr nach Gewicht in kg: bis einschließlich 5 kg kostet es 4,90 €, über 5 bis einschließlich 10 kg 6,90 €, über 10 bis einschließlich 31,5 kg 12,90 €. Ein Gewicht von 0 oder weniger und alles über 31,5 kg ist nicht versendbar: Die Funktion liefert dann None. Schreibe die Testfunktion test_gebuehr() mit mindestens acht assert-Zeilen, die jeden Bereich und jede Grenze von beiden Seiten prüft, und rufe sie am Ende auf. Die erwarteten Werte rechnest du aus der Beschreibung von Hand aus.

Für Neugierige. Nichts davon kommt in der Klausur dran.

pytest: das Test-Gerüst der Praxis (Ausblick)

Hinweis: pytest ist ein zusätzliches Paket und läuft in Codespaces oder auf deinem Rechner, nicht im Browser dieser Seite. Ampel: Delegieren. Du musst wissen, dass es das gibt.

# datei: test_lager.py   (Aufruf im Terminal: pytest)
from lager import zustand

def test_grenze_85():
    assert zustand(85) == "warnung"

def test_grenzen_schleife():
    faelle = [(69.9, "normal"), (70, "warnung"), (85.1, "abschalten")]
    for t, erwartet in faelle:
        assert zustand(t) == erwartet

Das Muster kennst du: Funktionen mit test_ am Anfang, darin assert. pytest findet alle solchen Funktionen in allen Dateien selbst, führt sie aus, zeigt je Test einen Punkt oder ein F und bei einem Fehler genau, welcher Wert erwartet und welcher bekommen wurde. Du musst dich nicht selbst um den Aufruf der Testfunktionen kümmern. Mit der Option --cov (Zusatzpaket) misst es, welcher Anteil deines Codes die Tests überhaupt durchlaufen.

Testgetrieben entwickeln und Regressionstests

Bei der testgetriebenen Entwicklung (englisch TDD, test-driven development) schreibst du zuerst den Test, dann den Code, der ihn besteht. Das ist die Arbeitsweise dieses Kurses ab V11: Spezifikation, Testfälle, dann generieren, dann prüfen. Ein Regressionstest ist ein Test, den du aufhebst, nachdem du einen Fehler gefunden hast: Der Fall, der den Fehler gezeigt hat (bei uns 85 °C), bleibt für immer in der Liste. Wer später am Code ändert, merkt sofort, wenn derselbe Fehler zurückkommt.

Der Debugger in VS Code im Detail

In Codespaces genügt es, die Datei zu öffnen, am Zeilenrand zu klicken (roter Punkt) und oben rechts auf „Python-Datei debuggen“ zu drücken. Mit einem Rechtsklick auf den Punkt kannst du einen bedingten Haltepunkt setzen, zum Beispiel w == 85.0: Das Programm hält erst dort, wenn die Bedingung stimmt. Im Fenster Überwachung trägst du Ausdrücke ein (t < 85), die bei jedem Schritt neu berechnet werden. In der Debug-Konsole darfst du Ausdrücke eintippen und sofort auswerten lassen. Das ist das Werkzeug der Wahl, wenn print zu unübersichtlich wird.

assert ist kein Prüfer für Benutzereingaben

Hinweis: Das geht über V12 hinaus (Klausur nicht erforderlich).

def wurzel_aus(x):
    if x < 0:
        raise ValueError("x darf nicht negativ sein")
    return x ** 0.5

try:
    wurzel_aus(-4)
except ValueError as fehler:
    print("Eingabefehler:", fehler)

Python kann mit der Option -O alle assert-Zeilen überspringen. Verlass dich darum nie auf ein assert, um Eingaben von Menschen oder Dateien zu prüfen. Dafür gibt es if mit raise, wie hier. Das assert ist für Tests und für Annahmen im Entwickler-Kopf da: „Hier muss die Liste mindestens ein Element haben.“
